## 4. The HU-translation decision (workstream B) — DECIDED: DeepL

**Decision (2026-04-30, editor):** translate via DeepL API, not LLM
batches. Pipeline lives in `scripts/deepl_translate.py`; full docs
in `DEEPL.md`.

Estimated total: 482 paper translations × 3 fields × ~700 chars
≈ **~1 M chars**. Fits in two months of DeepL Free
(500 k chars/month) or one month of DeepL Pro (€4.99 base + €20 /
1 M chars ≈ ~€25 one-shot).

Why DeepL over LLM batches:
- Higher fluency on Hungarian econ prose (test before committing).
- Deterministic output — no per-paper review needed for the bulk.
- Cheap at this scale.
- Glossary support keeps econ jargon and Hungarian institution
  names stable across the whole corpus.

Workflow (see `DEEPL.md` §2 for the full operator guide):

1. `python scripts/deepl_translate.py --dry-run` — preview the
   queue.
2. **Pilot one author** end-to-end (no glossary):
   `python scripts/deepl_translate.py --apply --author szentes-balazs`.
   Eyeball 3–5 random translations; commit if good.
3. **Create the glossary**:
   `python scripts/deepl_glossary.py create scripts/deepl_glossary_en_hu.tsv`,
   then `export DEEPL_GLOSSARY_ID=<id>`.
4. **Pilot author 2** with glossary; spot-check; compare against
   author 1.
5. **Bulk sweep** — `--apply` with no filter. Run by author batch
   so commits stay reviewable.
6. **Spot-check protocol**: 1 random paper per batch. Mistranslated
   recurring terms → add to TSV → recreate glossary.
7. Pause and re-decide if 2+ consecutive batches show >1
   mistranslation per summary.

Fallback if quality fails: hire a translator with a CSV export
(~€1500–3000 one-shot). Decision point after the first 3 author
batches.

Backup option if launch is urgent: ship with `summary_en` only and
a "HU translation in progress" banner; translate post-launch.

## 5. Author outreach (workstream G)

The dossier flow exists (`generate_dossier.py` + `OUTREACH.md`). The
scarce resource is **editor time on incoming replies**, not script
time.

Sequencing:

1. **Audit before sending.** Never send a dossier with known stub
   errors. Run `bulk_audit.py <slug>` first; close obvious gaps
   (missing repec_id, missing qualifying_pub, EN drafts).
2. **Wave-based, not bulk.** ~10 dossiers per wave, then wait one
   week for replies before the next wave. This caps the editor's
   reply backlog.
3. **Order:** start with authors who already replied positively in
   prior waves (carry-over from earlier handovers), then top-cited /
   most-senior, then everyone else. Most likely to reply: people
   who collaborate with the editor; least likely: diaspora full
   professors with no Hungary research interest.
4. **Treat replies as P0.** Same-day commit, `review_status →
   author-approved`, drop to `submissions/DONE/`.
5. **Special cases:** Kornai (deceased) and Simonovits press items
   pre-date the workflow — ship as-is; flag in About page.

Realistic yield: of 90 dossiers sent, expect 30–40 replies, mostly
within 2 weeks of send. After 4 weeks, anything outstanding is a
non-reply; ship without explicit approval but with the standard
"corrections welcome" footer.

## 6. Sequencing — 6 weeks

The cadence assumes ~1 Claude Code session/day (~1–2 hours editor
time on this project) with one longer cowork session per week.

**Week 1 — clear small queues, set up B.**
- Close all P3 (42 policy summaries). One-pass batching.

  lengyel, lindner, ~10 papers total).

  most-cited authors. Scriptable batch.
- **DeepL pilot**: get key, run `--usage`, run pilot on Szentes
  Balázs (19 P2) without glossary, eyeball, commit. Then create
  glossary, run a second pilot, compare. See `DEEPL.md`.

**Week 2 — HU bulk pass starts; outreach wave 1.**
- HU batches 1–6 (~150 papers), top-paper authors.
- Generate + send dossiers for the 10 most-likely-to-reply authors.
- Photo sweep for the same 10 (so the dossier reflects the page
  they'd land on).

**Week 3 — HU continues; outreach wave 2; first round of replies.**
- HU batches 7–12 (~150 papers).
- Process incoming replies (P0). Likely 4–8 in this week.
- Dossier wave 2: next 10.

**Week 4 — HU finish; PDF cowork session.**
- HU batches 13–17 (~150 papers, finishes the bulk).
- Cowork session: tackle the ~30 P1 papers that need PDF access
  (institutional library, author-supplied PDFs from replies).
- Dossier wave 3: next 10.

**Week 5 — cleanup pass.**
- All remaining P1, P3 = 0.
- DOI completion (Crossref pass + manual leftovers).
- Photo sweep for the remaining ~24 authors without one.
- Run `cross_check.py`, fix anything new.

**Week 6 — launch readiness.**
- Update About + Contribute pages.
- Write press kit (1-pager + 3 case-study paper links).
- Final audit; tag a launch commit.
- Editor decides: announce now or hold for the policy moment.

After week 6: maintenance mode (quarterly sweeps; incoming
submissions; new top-journal placements).

## 7. Background info needed — per author

For every author JSON, target this completeness:

- `name_en`, `name_hu` ✓ (already populated)
- `affiliations` — current primary + ≤2 past
- `website`
- `email` — in `not-shared/contacts.json`, not in JSON

- `orcid`
- `bio_en` — 80–110 words, structure per memory rule
- `bio_hu` — parallel
- `photo_url` — institutional or personal-site URL. **34 missing.**
- `qualifying_publication` — title + journal + year of the entry
  Tier-A/B paper. **36 missing.**
- `primary_fields` — 2–3 from the topic vocabulary
- `deceased` / `died` — only if applicable
- `open_to_media_en` / `open_to_media_hu` — author-supplied
- `media_note` — author-supplied

Sourcing order: IDEAS profile → personal website → CEPR/CEU/Corvinus
faculty page → Scholar → CV (if author supplied) → dossier reply.

## 8. Background info needed — per paper

For every paper JSON, target:

- `id`, `title`, `authors` (slugs where possible)
- `publication_type`, `year`, `journal`, `volume`/`issue`/`pages`
- `doi` — null only if paper genuinely pre-dates DOI
- `url_published`, `url_pdf`, `url_replication` (where exists)
- `abstract` — verbatim publisher abstract; if missing, draft
  marked as such
- `summary_en`, `summary_hu`, `data_used`, `data_used_hu`,
  `policy_relevance`, `policy_relevance_hu`
- `topics` (1–3 from controlled vocab), `methods` (1–2),
  `data_types` (1–3), `countries_studied`
- `policy_instruments` — free-text array, optional
- `review_status` — set as it progresses

Sourcing order: IDEAS publication record → Crossref → publisher
page → SSRN/RePEc abstract page → author website → PDF (last
resort).

For policy and press items: see SPEC §2.6 / §2.7. The same fields
apply with the smaller schemas.

## 9. Where the work happens

**Stay in Claude Code:**
- All JSON edits (papers, authors, policy, press).
- All drafting (EN and HU summaries, bios).
- All scripts (`apply_drafts`, `apply_summaries_hu`, `cross_check`,
  `bulk_audit`, dossier generation).
- Audits, drift control, validation.
- Web-fetching abstracts, photos, DOIs (WebFetch / WebSearch).
- Generating outreach dossiers.

**Leave Claude Code for:**
- **Sending email** (Gmail or whatever client). Do not paste author
  emails into model prompts. The dossier is content; the send is
  manual.
- **PDF retrieval for institutional-only papers** (CEU library,
  SciHub-equivalent only if licensed). Save the PDF to
  `not-shared/pdfs/`, then come back to Claude Code to draft.
- **Author CV intake.** Save to `not-shared/cvs/<slug>/`; come back.
- **Domain / DNS / hosting changes.** One-offs at launch.
- **Optional:** outsourced HU translation (Option 2 in §4) —
  CSV out, translator fills, CSV back in.

**Decision principle:** Claude Code handles anything that touches
the JSON layer or scripts. Anything that touches *people* (sending
mail, reading replies, getting a CV) happens in regular tools, with
artifacts dropped back into the repo for processing.

|---|---|
| Author dissatisfaction with their entry | Audit before sending dossier. Never send with known stub errors. |
| Bad HU translations going public | Spot-check 1 in 5 in the pilot. Switch to Opus or to a human translator if drift detected. |

| Editor reply backlog | Wave-based outreach (10 at a time, 1 week apart). |
